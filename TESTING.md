# Testing

- `npm run test` (Vitest, `src/**/*.test.ts`, node, no network/model/Supabase) — the deterministic spec checks: D1-D3, E1, E2, E3, F1, F2, G1, G2, G3, G4, G5, H1, H3, H4, R8.4/B3, H5/R3.1/R4.2, B2/R4.1, H2/R5.2/R5.4.
- `npm run typecheck` (includes the tests), `npm run lint` (baseline: 0 errors / 0 warnings) and `npm run build` must all pass clean.
- `npm run harness` runs the live-model checks (B1, C1, C2); it needs `.env` and network access, costs money and varies run to run, so judge it over two runs.
- Not covered by any automated test, anywhere: A (build health is the commands above, run by hand or CI, not a test), the live-model checks B1, C1, C2 (harness only, see above), and everything that needs a real database (listed per check below: the Supabase calls themselves, row-level atomicity, realtime). The pure logic behind every one of those database writes is tested; the writes are not.

- G5 (single driver, R7.6/R9.4) is covered by `src/sim/__tests__/driver.test.ts`: the pure lease rules in `src/sim/driver.ts` (`decideLease` table including the TTL boundary, `leaseCutoffIso`, the claim filter and its id safety, a source guard that the module reads no clock) and two competing drivers against an in-memory fake of the `sessions` row that parses the real filter string. What is **not** tested: the atomicity itself. It holds by construction because acquisition is one conditional `UPDATE ... WHERE id = ? AND (driver_id IS NULL OR driver_id = me OR heartbeat missing or stale) RETURNING *`, and Postgres serialises competing updates on a row; there is no database in this environment, so the unit tests do not run that statement against one, nor `Simulation.start()`/heartbeat/release (`simulation.ts` imports Supabase). Verify on a real database with two browser windows.

- E1 / E2 (save and resume, R9.1-R9.3, R6.5) are covered by `src/sim/__tests__/checkpoint.test.ts` against the pure `src/sim/checkpoint.ts`. E1 builds a rich world with the real engine (a gathered animal with its respawn due-tick, a depleted mine, a built house, a thrown cube, trained skills, goals, two chats waiting in an inbox, bonds, the turn cursor mid-cycle), builds a checkpoint at tick T, runs the world on until every item has moved, restores (through a JSON round trip, as the database stores it) and asserts every R9.2 item equals its value at T, that each villager's `observe()` text is identical to the one captured at T, that the payload holds only state keys (no events, memories, history or clock) and that neither building nor restoring shares a reference with the live world. E2 refuses a checkpoint stamped with another rules version, with a moved seed object, with no fingerprint, with an old-format row (no version) and with an unknown version, each with a plain message, and refuses damaged payloads without throwing. The same file proves the replay scrubber (`toReplayCheckpoint`, `nearestCheckpoint`) still reads old-format rows (with and without a fingerprint) and new ones, and that a fork's villagers can be given new ids with bonds, pending messages and the turn cursor following.
- D1-D3 (memory) are covered by `src/sim/__tests__/memory.test.ts` against the pure `src/sim/memory.ts`. D1: a `discover` (written from the engine's own result) reaches another villager, a `remember` does not. D2: a new namesake inherits knowledge, discoveries and diary capped 6 / 6 / 8 from the latest 30; an ordinary era is layered exactly as the old `getMemories` was (a verbatim reference copy is compared on representative rows); an amnesiac era inherits nothing from other eras; a fork sees the parent's rows with tick <= the fork tick and its ancestors' rows up to their own fork ticks, never later rows nor eras outside its line; the database-side `.or(...)` filter is proven equal to the in-code rule by a small evaluator over every era/tick combination. D3: `diaryEntryFor` gives an entry for every successful action type except the two that write their own memory (`remember`, `discover`; a `plan` is unrolled and a nested plan always fails), and none for failures; a source check confirms `simulation.ts` goes through it and stamps both memory writes with era and tick.
- What is **not** exercised against a real database or by an automated test: `Simulation.forkFromCheckpoint` (its reads of `sessions`/`checkpoints`, ending the live era, the inserts into `sessions`, `agents`, `structures`, `civ` and `depleted_objects`, the lease claim and the best-effort clean-up on failure), `getMemories`' two Supabase queries and the `.or(...)` string as PostgREST parses it (only its equality with the in-code rule is tested), `loadWorld`'s new continue-from-last-tick lookup, `maybeCheckpoint`'s write, the "Continue from here" control, and the two migrations (`20261027190000_stamp_memories_with_tick.sql`, `20261027190100_add_session_fork_support.sql`). `simulation.ts` imports Supabase and is deliberately not imported by tests. The migrations were applied in order, on top of all earlier ones, to a scratch PostgreSQL 16 with stub `anon`/`authenticated` roles and an empty `supabase_realtime` publication (they apply cleanly; the same structures id under two eras is accepted and a duplicate within one era is refused), which is not a Supabase project: verify on a real database, then fork an archived era by hand (a fingerprint mismatch, an era without checkpoints, and a second window holding the lease are the three refusals to try).

- G1 (bond symmetry, R7.1) is covered by `src/sim/__tests__/bonds.test.ts` against the pure `src/sim/bonds.ts`. Two and three villagers act through the real engine `step()`; the bookkeeping is the same `recordBond` path `simulation.ts` uses, with the database replaced by a list of the rows it would be asked to write. A chat adds exactly +1 to both villagers' bonds, a gift exactly +2, in either direction; the last-exchange text is kept on both sides ("gave wood" / "received wood" for a gift); a failed chat or gift (too far, hands full) and every other action leave the bonds alone; mixed exchanges accumulate (3 chats + 2 gifts = 7 on each side, and the two sides are equal after every one of 40 mixed exchanges); a third villager's bonds, and the pair's bonds with that third villager, never move; the pair row written is the sorted `(a_id, b_id)` row with the new strength and the era. **Found and fixed:** `simulation.ts` bumped a gift by +1 (its own comment said "twice as much as a chat") against the spec's +2/+2; the amounts now live in one table, `BOND_DELTA`. What is **not** tested: that Postgres really holds those rows (the upsert is not run against a database), and bonds inherited by namesake on load (`getRelationships`, database reads).
- H4 (bond persistence retry, R7.1) is covered by `src/sim/__tests__/bondPersistence.test.ts`. The write goes through `createBondWriter(persist)`; `persist` is replaced by a fake `relationships` table whose calls can be scripted to reject. With the first side's write rejecting: both in-memory bonds are already correct, the next write for the pair persists the **latest** strength (never the stale one that failed), nothing stays dirty afterwards, a failure of one pair is retried by a write of any other pair, a database that stays down for several exchanges keeps failing quietly while the bonds keep growing in memory and the first success writes the latest value, a failure (even a synchronous throw) never reaches the turn that caused it, and writes are serialized so a slow older write cannot land after a newer one. With a healthy database an exchange is exactly two upserts (actor side, then target side), as before. **Added:** the retry did not exist (a failed upsert was ignored or only logged, and the bond stayed stale in the database until some later exchange happened to rewrite it); the pending set is in memory only, so a page reload with a write still dirty loses the retry (the next exchange of that pair rewrites the row, and the first bump of a bond after a reload converges as it always did). What is **not** tested: that `supabase.from('relationships').upsert(...)` rejects the way the fake does (it returns `{ error }`; `persistBond` turns that into a rejection, which is a source-level check only, and there is no database here).
- G2 (no double occupancy, section 7 "Space") is covered by `src/sim/__tests__/space.test.ts`. Six seeded runs of 2,500 turns each (3 or 4 villagers on the real island, `Math.random` stubbed with the seeded PRNG from `fixtures.ts`), turns taken in cursor rotation with `pickNextActor`, each turn a random valid-ish action (goto including off-map and beside-a-neighbour targets, move, wander, gather, gather_nearest, deposit, pick_up, place, throw including at the Standing Rock, build, chat, gift, and 2-4 step plans run through `runSteps`). After **every step** (not every turn) the test asserts no two villagers share a tile, nobody stands in water or off the grid, and no two cubes share a tile; and that a cube set down or thrown onto open ground never lands on a tile that already held an object. Across the runs every listed action both succeeded and failed at least once (wander only succeeded, it is never boxed in), so the runs do exercise the rules rather than only waiting. Also: a newcomer joining a running world (`findSpawnTile`) is placed on a free tile inside its territory, never on a villager, until the territory is full, preferring bare ground; the manifest's starting cast stands on distinct tiles of their own territories; the checker itself reports a shared tile, a villager in water and stacked cubes. **Found and fixed:** (1) the Standing Rock drew its two new cubes from the free tiles around it *with* replacement, so both could land on the same tile (seed 4, turn 1215 of the first run); it now draws two different tiles. (2) `addAgent` placed a joining villager at a random `(2..6, 2..6)` whatever its chosen territory and whether or not a villager already stood there; it now uses `findSpawnTile`. What is **not** tested: `addAgent` itself (it inserts into the database), and positions loaded from the database by `loadWorld`, which are trusted as saved.
- H1 (what the mind is given, R8.1/R7.2/R5.3) is covered by `src/sim/__tests__/mind.test.ts` against `src/sim/mind.ts` (`buildMindInput`, which `simulation.ts` now calls for every turn instead of calling `systemPrompt` and `observe` itself). The section headings of the system prompt are asserted against an explicit constant (persona + soul, skills, territories, chronicles, bonds, action catalog with its world rules) and every other non-list line against an explicit list of allowed prose lines; the observation is checked line by line against an explicit list of allowed line openings (and a test fails if that list goes stale). Add a section and these tests fail until the spec is reviewed (checked once by hand by adding a heading). With two villagers holding distinct secrets in their persona, inventory, thought, bubble, goals, skills, bonds, pending inbox, model, status and private memory: none of Bramble's secrets appears in Alder's mind, while they do appear in Bramble's own (so the check would catch a leak), and what section 5 calls common knowledge does appear (name, mood, territory, position, standing beside). The shared discovery is in both minds and each private memory only in its owner's, also end to end through `layerMemories`; fifty rows layer into at most 6 + 6 + 8 chronicle lines; no `[object Object]`, `undefined`, `null`, `NaN`, no full uuid (only the 8-character short id of a neighbour standing beside), no `session_id`/`created_at`/other column names; unknown fields planted on the villager or world (stand-ins for player text and database rows) are never printed; the same inputs give the same mind byte for byte without changing them, and a changed world, chronicle, bond or history shows on the very next build. What is **not** tested: that `getMemories` really returns only the villager's own rows plus discoveries from the database (its pure layering is D1/D2; the two queries are not run), the edge function, and the model's reply.
- H3 (chronicle completeness, R3.3/R8.4) is covered by `src/sim/__tests__/chronicle.test.ts` against `src/sim/chronicle.ts` (`eventsForResult`, `planEndRow`), whose rows `simulation.ts` writes verbatim with `logEvent`. For every one of the 21 action types the real `step()` is run in a situation it accepts and, where the world can refuse it at all, one it refuses (`say`, `remember`, `train`, `discover`, `set_goal` and `wait` can never fail): each yields a row of that action's type whose message is the world's own answer, with a plain-language reason when refused. A private `remember` is chronicled as the world's summary line carrying the entry (visible or summarized, never dropped; long entries are cut at the engine's 500 characters). Plans are run through the same `planSteps`/`runSteps` the simulation uses: a 3-step plan writes 3 action rows (+1 thought row for the turn), one that fails at step 2 of 3 writes steps 1 and 2 with the reason and "plan ends at step 2 of 3" and never runs step 3, a failure at the last step has no "plan ends" row (every step ran), a failure at step 1 of 4 says so, plans of 2-4 steps write one row per executed step; the thought is written once, on the first step; a chat that pushes out the target's oldest unheard words also chronicles the loss under the target. Source checks confirm `simulation.ts` goes through these two functions and chronicles before it persists anything for the result. No behavior change: the same rows are written in the same order; only the code that builds them moved. What is **not** tested: that the rows arrive in the `events` table (`logEvent`'s insert), the level-up rows (still built inline from `grantXp`), the fallback/mismatch system row for unparseable replies, and the order of events relative to memory inserts across tables.
- Still not covered by any automated test: the Supabase layer as a whole (`Simulation.start/heartbeat/forkFromCheckpoint/loadWorld/getMemories/getRelationships/addAgent/removeAgent`, `maybeCheckpoint`'s write, the migrations on a real Supabase project), the React UI, the live-model checks B1/C1/C2, and A as a test. The retry set of H4 and the lease of G5 are in memory / pure logic only.
