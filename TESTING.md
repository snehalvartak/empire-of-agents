# Testing

- `npm run test` (Vitest, `src/**/*.test.ts`, node, no network/model/Supabase) — the deterministic spec checks: D1-D3, E1, E2, E3, G3, G4, G5, R8.4/B3, H5/R3.1/R4.2, B2/R4.1, H2/R5.2/R5.4.
- `npm run typecheck` (includes the tests), `npm run lint` (baseline: 0 errors / 0 warnings) and `npm run build` must all pass clean.
- `npm run harness` runs the live-model checks (B1, C1, C2); it needs `.env` and network access, costs money and varies run to run, so judge it over two runs.
- Not covered yet: A (build health is the three commands above), F, G1/G2, H1/H3/H4 (they need persistence or manifests that are not built).

- G5 (single driver, R7.6/R9.4) is covered by `src/sim/__tests__/driver.test.ts`: the pure lease rules in `src/sim/driver.ts` (`decideLease` table including the TTL boundary, `leaseCutoffIso`, the claim filter and its id safety, a source guard that the module reads no clock) and two competing drivers against an in-memory fake of the `sessions` row that parses the real filter string. What is **not** tested: the atomicity itself. It holds by construction because acquisition is one conditional `UPDATE ... WHERE id = ? AND (driver_id IS NULL OR driver_id = me OR heartbeat missing or stale) RETURNING *`, and Postgres serialises competing updates on a row; there is no database in this environment, so the unit tests do not run that statement against one, nor `Simulation.start()`/heartbeat/release (`simulation.ts` imports Supabase). Verify on a real database with two browser windows.

- E1 / E2 (save and resume, R9.1-R9.3, R6.5) are covered by `src/sim/__tests__/checkpoint.test.ts` against the pure `src/sim/checkpoint.ts`. E1 builds a rich world with the real engine (a gathered animal with its respawn due-tick, a depleted mine, a built house, a thrown cube, trained skills, goals, two chats waiting in an inbox, bonds, the turn cursor mid-cycle), builds a checkpoint at tick T, runs the world on until every item has moved, restores (through a JSON round trip, as the database stores it) and asserts every R9.2 item equals its value at T, that each villager's `observe()` text is identical to the one captured at T, that the payload holds only state keys (no events, memories, history or clock) and that neither building nor restoring shares a reference with the live world. E2 refuses a checkpoint stamped with another rules version, with a moved seed object, with no fingerprint, with an old-format row (no version) and with an unknown version, each with a plain message, and refuses damaged payloads without throwing. The same file proves the replay scrubber (`toReplayCheckpoint`, `nearestCheckpoint`) still reads old-format rows (with and without a fingerprint) and new ones, and that a fork's villagers can be given new ids with bonds, pending messages and the turn cursor following.
- D1-D3 (memory) are covered by `src/sim/__tests__/memory.test.ts` against the pure `src/sim/memory.ts`. D1: a `discover` (written from the engine's own result) reaches another villager, a `remember` does not. D2: a new namesake inherits knowledge, discoveries and diary capped 6 / 6 / 8 from the latest 30; an ordinary era is layered exactly as the old `getMemories` was (a verbatim reference copy is compared on representative rows); an amnesiac era inherits nothing from other eras; a fork sees the parent's rows with tick <= the fork tick and its ancestors' rows up to their own fork ticks, never later rows nor eras outside its line; the database-side `.or(...)` filter is proven equal to the in-code rule by a small evaluator over every era/tick combination. D3: `diaryEntryFor` gives an entry for every successful action type except the two that write their own memory (`remember`, `discover`; a `plan` is unrolled and a nested plan always fails), and none for failures; a source check confirms `simulation.ts` goes through it and stamps both memory writes with era and tick.
- What is **not** exercised against a real database or by an automated test: `Simulation.forkFromCheckpoint` (its reads of `sessions`/`checkpoints`, ending the live era, the inserts into `sessions`, `agents`, `structures`, `civ` and `depleted_objects`, the lease claim and the best-effort clean-up on failure), `getMemories`' two Supabase queries and the `.or(...)` string as PostgREST parses it (only its equality with the in-code rule is tested), `loadWorld`'s new continue-from-last-tick lookup, `maybeCheckpoint`'s write, the "Continue from here" control, and the two migrations (`20261027190000_stamp_memories_with_tick.sql`, `20261027190100_add_session_fork_support.sql`). `simulation.ts` imports Supabase and is deliberately not imported by tests. The migrations were applied in order, on top of all earlier ones, to a scratch PostgreSQL 16 with stub `anon`/`authenticated` roles and an empty `supabase_realtime` publication (they apply cleanly; the same structures id under two eras is accepted and a duplicate within one era is refused), which is not a Supabase project: verify on a real database, then fork an archived era by hand (a fingerprint mismatch, an era without checkpoints, and a second window holding the lease are the three refusals to try).
