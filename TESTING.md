- H4 (bond persistence retry, R7.1) is covered by `src/sim/__tests__/bondPersistence.test.ts`. The write goes through `createBondWriter(persist)`; `persist` is replaced by a fake `relationships` table whose calls can be scripted to reject. With the first side's write rejecting: both in-memory bonds are already correct, the next write for the pair persists the **latest** strength (never the stale one that failed), nothing stays dirty afterwards, a failure of one pair is retried by a write of any other pair, a database that stays down for several exchanges keeps failing quietly while the bonds keep growing in memory and the first success writes the latest value, a failure (even a synchronous throw) never reaches the turn that caused it, and writes are serialized so a slow older write cannot land after a newer one. With a healthy database an exchange is exactly two upserts (actor side, then target side), as before. **Added:** the retry did not exist (a failed upsert was ignored or only logged, and the bond stayed stale in the database until some later exchange happened to rewrite it). **Then found:** the pending set was in memory only, so a failed upsert followed by a page reload lost the correction (the database kept the stale strength, the reloaded villagers read it, and the pair silently lost an exchange); it is now durable, see the next item. What is **not** tested: that `supabase.from('relationships').upsert(...)` rejects the way the fake does (it returns `{ error }`; `persistBond` turns that into a `BondWriteError` carrying `error.code` and the HTTP status, which is a source-level check only, and there is no database here); the e2e scenario g below runs it against a real PostgREST.
- H4 durable (the bond retry set survives a page reload, R7.1) is covered by `src/sim/__tests__/bondStore.test.ts` (41 tests) against the pure `bonds.ts` and `bondStore.ts`; it imports no Supabase. `createBondWriter(persist, store?)` takes an optional synchronous `BondStore { load(): PairRow[]; save(rows) }`: it seeds its pending map from `load()` (each row validated again, at most 200, the higher strength wins for a pair) and saves on every change of the set. A row is saved **before** its request is made and removed when the request succeeds, so a page that unloads while a request is in flight still has the row on its next load (the retry is an idempotent upsert); `clear()` (new era, fork, reset) empties the store too. The browser adapter `bondStore.ts` keeps `{v:1, rows}` under `localStorage['empire:dirty-bonds:v1']` (ids, strengths and timestamps only; no names, messages or keys). The storage is looked up when used, never at import; any failure (no storage, a throwing getter, quota, private mode, corrupt or foreign or oversized content, a wrong version, a malformed row, more than 200 rows, ids that are not uuids, a negative / fractional / out-of-range strength) reads as nothing or is swallowed, and the writer carries on from memory (a save that failed is tried again at the next change). Tested: validation table; stored-text round trip; garbage never throws; only the bad rows are dropped; the cap keeps the newest; a failed write is stored, and a NEW writer built from the same store (a reload) flushes it on the next bond write (of any pair) and empties the store; building a writer writes nothing (so a watcher never flushes); success removes the row; the row is in the store while its request is in flight; `clear()` empties it and a row cleared mid-flush is not written back; storage that throws on load, on save or on both degrades to memory-only (and a storage that comes back catches up); a newer write for a pair replaces the stored row, never the reverse.
  - **Permanent vs transient (what `persistBond` throws).** supabase-js returns `{ error }` with PostgREST's body, whose `code` is the PostgreSQL SQLSTATE; `persistBond` rethrows it as `BondWriteError(message, error.code, status)`. A write is **permanent** (the row is dropped from memory and store, never retried) iff the code is SQLSTATE class 23 (integrity: `23503` foreign key, i.e. a villager of the pair no longer exists, a dismissed villager or a deleted era; `23502`, `23514`, ...) or class 22 (data exception: `22P02` malformed uuid, `22003` integer out of range). Everything else is **transient** and keeps the row: no response (network, DNS, CORS, offline: no code or a Node/browser error code, status 0), 5xx and gateway errors with or without a JSON body, 408, 429, PostgREST's own `PGRST*` codes, auth/permission errors (`42501`, 401/403: a deployment problem a fix makes succeed, so the correction is worth keeping), and a plain `Error`. Tested as a table, with the writer dropping a stored row on its first retry while another row of the same batch keeps failing with a 503 and stays. Not tested: that the live database really answers `23503` (the e2e does not delete a villager mid-run), and a row that fails transiently for ever stays until a success, a newer write for the pair, `clear()`, or the 200-row cap evicts it.
  - **Stale versus newer.** A bond only grows (chat +1, gift +2, nothing subtracts), so for one pair the larger strength is the later one and no clock is needed. After the reload hydrated the cache from the database and before any turn runs, `Simulation.recoverBonds` reads the pair's strength and applies the pure `recoveryFor(row, stored)`: **write only if the database has no row or a strictly lower strength**; a row that is equal (already persisted) or lower (overtaken by another window) is dropped and never overwrites a higher value (the database is not asked to compare-and-set, so this is read-then-write; the only writers are the lease holder and a free window, see below). The in-memory bonds of both villagers (the `relationshipsCache` maps that prompts and checkpoints read) are raised to every pending row's strength (`raiseBondsFromRows` / `raiseBond`: never lowered, a missing bond or map created, a bond that still names an earlier era's namesake re-pointed at this era's villager, rows whose villagers are not both on the roster skipped), otherwise the next exchange would build on the stale database value and the new row would replace the stored correction. This raise runs **after every (re)load of the cache** (`hydrateRelationships` ends with it, and `recoverBonds` repeats it), so it does not matter whether the flush comes before or after `loadWorld` filled the cache: a load replaces the maps with the table's (possibly stale) values and the pending rows are re-applied on top; a watching window does the same raise (display only) but never writes. A newer write for the same pair in the same page replaces the stored row. Tested: the `recoveryFor` table, `raiseBond` (including the inherited-namesake re-point), `raiseBondsFromRows` (both sides, other eras skipped, idempotent, never lowers, empty cache then a replaced cache), a **simulated reload** (page 1 writes 1, 2, then a gift to 4 with the database down after 2; page 2 reads the stale 2, recovers: database and both villagers at 4, store empty, the next exchange gives 5), a stale row (database at 9 or already at the row's value) writes nothing and lowers nothing, and a first-ever bond that never reached the database comes back from the store.
  - **Found by the e2e and fixed: bonds inherited from an earlier era wrote the wrong rows.** `getRelationships` loads a new era's bonds by villager *name* from every era's namesakes, so a bond's `withId` was the earlier era's villager; `bump` never changed it and `pairRowFor` builds the row from `bond.withId`, so one chat wrote two different rows, (this Alder, earlier Bramble) and (earlier Alder, this Bramble), and never the era's own pair, which also left the pending rows unmatched to the roster (no recovery). `bump` and `raiseBond` now re-point the bond at the villager it is really with, and where several rows name the same villager `preferBond` picks the villager's own row, then the stronger (it used to be whichever row the database returned last). Tested in `bondStore.test.ts` (`preferBond` table; an exchange between villagers whose bonds were inherited writes ONE row of this era's two ids) and by the e2e scenario g (the healthy chat's upserts name this era's two agents).
  - **Who may flush (R7.6).** `recoverBonds` runs at the end of `loadWorld`, after the cache is hydrated, and its first statement is `if (this.readOnly) return;`: a watching window loads the rows and never writes them; when it takes the lease over, `start()` reloads the world (`loadWorld(true)`) and recovers then. A window that is free (nobody drives the era) also recovers on load, without holding the lease: it can only be there when no live driver exists, and the recovery is the same conditional correction. Source checks pin this wiring (the guard is the first statement, the call follows `hydrateRelationships`, the writer is built with the browser store, `clear()` is still called in the three places), and that `bonds.ts` / `bondStore.ts` read no clock and no `window`.
  - **Design change from the brief:** the row is saved before the request rather than after the failure (a page unloading mid-request would otherwise lose it). The existing `bonds.test.ts` and the `bondPersistence.test.ts` tests run unchanged; the one adaptation is the source guard that pinned the exact text `createBondWriter((row) => this.persistBond(row))`, now `createBondWriter((row) => this.persistBond(row), browserBondStore())`.
  - **Not covered:** cross-tab (two tabs of the same browser profile share one `localStorage` key and one tab's save overwrites the other's set; a row the second tab never held can be lost, and two free tabs would each recover; the 30 s lease protects the era, not this key), the user clearing site data or using another browser profile / device (the dirty row lives only in that profile; the database keeps the stale strength and the pair loses that exchange, as before this change), a browser that blocks `localStorage` (memory-only, as before), private windows that discard storage on close, a recovery whose pair read fails (the row is kept and is flushed by the next bond write **without** the stale check), rows left by an archived era (a pending row whose villagers are not on the current roster is kept and written by the next flush if the database has no row or a lower value; it is never raised into memory, and `clear()` for a new era, fork or reset removes it; a row of a deleted villager is dropped on its first `23503`), a pair already ahead in the database from a window other than the one holding the row (handled only by the read-then-write rule above, not compare-and-set), and a write the server accepted but whose response was lost (the retry is an idempotent upsert of the same strength, so it is harmless). The unit tests use a fake `Storage`; the real `localStorage` is exercised only by the e2e scenario g.

## Checks outside `npm test`

Neither of these runs in `npm test` (no CI wiring, they need extra tooling), and each states what it cannot show.

### `npm run check:migrations` - the migrations on a real PostgreSQL 16

One command (`bash scripts/check-migrations.sh`; ~15 s). It needs the PostgreSQL 16 server binaries (`PG_BIN`, default `/usr/lib/postgresql/16/bin`: initdb, pg_ctl, psql, pg_dump) and Node >= 22.18. It starts a throwaway cluster in a temp dir on a free loopback port (as root it runs the server as the `postgres` OS user, or a throwaway user it deletes afterwards; everything is removed on exit) and prints a PASS/FAIL list; it exits non-zero if anything fails and names the migration file that failed.

What it does: creates stand-ins for what a Supabase project provides (`anon`, `authenticated`, `service_role` roles and an empty `supabase_realtime` publication; each is commented in the script); applies every file of `supabase/migrations` in filename order with `ON_ERROR_STOP`; asserts the columns and types added by the recent migrations (`sessions.driver_id`/`driver_heartbeat_at`/`parent_session_id`/`fork_tick`, `memories.session_id`/`tick`, `depleted_objects.respawn_tick`, `events.tick`, and the persisted villager state: `agents.inventory`/`inbox` jsonb NOT NULL default `'[]'` (a villager that existed before the migration is backfilled, an insert without them gets the defaults, NULL is refused, items/chat/cursor store and read back as the app writes them) and the nullable `sessions.last_actor_id`/`last_actor_index` (a pre-existing era reads NULL, no foreign key on the villager)), `checkpoints`, the `structures` key (unique `(session_id, id)`, no primary key; the same id under two eras is accepted, a duplicate within one era refused) and the realtime publication membership; applies the whole set a **second time** and asserts that every file applies and the schema dump is identical; seeds a legacy animal row (`respawn_at` set, `respawn_tick` null) and a mine row before the `respawn_tick` migration and asserts the animal is deleted and the mine survives (and that a modern animal row survives the re-run); and races the single-driver lease claim: `leaseClaimFilter()` from `src/sim/driver.ts` is called for the PostgREST `.or()` string, which the script translates term by term to SQL (an operator it cannot translate aborts, so a changed filter cannot silently go untested), then two separate `psql` sessions, released together by an advisory-lock barrier, run the conditional `UPDATE ... RETURNING id` for 50 rounds (half of them holding the row lock for 20 ms so the loser really waits and re-evaluates the predicate) and exactly one must win every round and be the row's holder; also checked: a fresh lease is refused, a stale one (> 30 s, and exactly at the cutoff) is taken over, a driver without heartbeat is taken over, the holder renews.

What it does **not** prove: this is not a Supabase project. PostgREST is not involved, so how it parses the `.or(...)` string is untested (only the equivalent SQL is); RLS is not exercised as `anon` (the stub roles are bare and every statement runs as the superuser, so policies and grants are only checked to exist in the migrations' own terms: RLS enabled, schema identical on re-run); realtime delivery is not exercised (only which tables the migrations add to the publication); Supabase-managed schemas (`auth`, `storage`, extensions) are absent, which no current migration needs.

**Found and fixed:** `20261027032927_enable_realtime_for_feed_tables.sql` was the only migration that was not re-runnable (`ALTER PUBLICATION ... ADD TABLE` fails with "already member of publication" the second time). It now skips tables that are already members; the first run does exactly what it did before. All other migrations apply a second time as a no-op.

### `npm run harness:smoke` - the harness end to end against a stub

One command (`node scripts/harness-smoke.mjs`, a few seconds, no network, no key, no cost). It starts `scripts/stub-model-server.mjs` (a dependency-free `node:http` server that answers `POST /functions/v1/agent-brain` in the real function's response shape, with a scripted policy: gather when a resource is in reach, deposit beside the Town Center, otherwise goto the Town Center / the first `goto` hint / wander) and runs the real harness against it as a child process (`HARNESS_SUPABASE_URL`, `HARNESS_SUPABASE_ANON_KEY`, `HARNESS_OUT_DIR` = a fresh temp dir; unset, the harness behaves exactly as before: `.env` and `script-results/`). Every 15th turn the stub deliberately misbehaves, in rotation: an invalid-JSON reply (its retry is also bad every other time), a thought that does not describe its action, and a 3-step plan whose thought names all three steps. The script asserts exit code 0, one JSON line in the temp dir and none added to the repo's `script-results/agent-loop.jsonl`, non-zero turns, fallbacks, mismatches and plans, a high gather success rate, and that the stub saw the retries and the wrong-key refusal; the stub and the temp dir are removed in every case.

**This verifies the harness plumbing and the app's own parse / retry / mismatch / plan code paths end to end over HTTP. It says NOTHING about real-model quality.** The "model" is a fixed script, so the live-model targets (C1 fallback/mismatch/wait rates, C2 honesty) remain **unmeasured** until someone runs `npm run harness` with a real key (judge over two runs). The plan-mismatch counter (a plan whose thought leaves a step uncovered) is not exercised by the stub.

### Real end-to-end (`npm run e2e`)

**Not part of `npm test`** (no CI wiring; it needs PostgreSQL 16 binaries, a Chromium that Playwright can launch, Node >= 22.18 and, the first time, network access to Docker Hub). One command, about 2.5-3 minutes after the PostgREST binary is cached: `npm run e2e`. It prints PASS/FAIL lines plus NOTE lines (findings that are not pass/fail), exits non-zero if anything failed, and removes every process, database directory and throwaway OS user in all cases. Env: `E2E_OUT_DIR` (where the screenshots and the built bundle go; default a fresh temp dir, printed at the start and the end; nothing is ever written inside the repo), `E2E_CACHE_DIR` (PostgREST binary cache, default `<tmp>/empire-of-agents-e2e-cache`), `PG_BIN`, `POSTGREST_VERSION` (default `v13.0.8`), `E2E_HEADED=1`, `E2E_ONLY="a,d (chat)"` (a development aid that runs only the named scenarios).

What runs for real: the production bundle (`vite build` against the local backend, the same code as `npm run build`), the real `@supabase/supabase-js` client, **all 21 SQL migrations** on a scratch PostgreSQL 16, a **real PostgREST** (`scripts/e2e/fetch-postgrest.mjs` downloads the static binary from the Docker Hub registry HTTP API, no docker daemon and no GitHub; `db-anon-role = "anon"`, `db-schemas = "public"`, an HS256 `jwt-secret`, `db-max-rows = 1000`, a non-superuser `authenticator` login role like Supabase's), JWTs signed by `scripts/e2e/jwt.mjs` and a real headless Chromium (software WebGL) driven with Playwright. `scripts/e2e/gateway.mjs` plays the part of Supabase's API gateway on one port: `/rest/v1/*` goes to PostgREST untouched (and every request is logged, so the test can show the URL the client really sent), `/functions/v1/agent-brain` is the stub model server's handler (`scripts/stub-model-server.mjs`), `/functions/v1/settings-key` answers `{set:true}`, and websocket upgrades on `/realtime/v1` are refused. **Faked: the language model** (a scripted policy; one reply per scenario can be chosen by the test so the app produces a chat) and **Supabase Realtime**.

What it proves, each asserted against both the UI and the database:
- **a) First load, new session.** The app attaches to the era the migrations left, seeds Alder and Bramble at the manifest's positions, territories, colours and personas with empty hands, shows the WebGL island and "Key set"; ending the (empty) era archives it with a title the (stub) model wrote and shows the continue button disabled for want of a checkpoint; "New session" founds a second era with the same cast.
- **b) A run.** Pressing Begin on the real conditional `UPDATE ... or(...)` sets `sessions.driver_id`; ticks advance at the fastest speed; `agent_positions` has one row per tick (1..N, no gaps, no duplicates, also across a reload and a takeover), `events` rows carry ticks, `agents.hunger` is exactly 4 per own turn, energy falls, `agents.inventory` and `agents.inbox` (jsonb) are written, memories carry era and tick, the heartbeat is renewed, a checkpoint row exists at tick 50 with the expected payload (version, fingerprint, cursor, both villagers) and `UNIQUE (session_id, tick)` holds.
- **c) Single driver.** A second browser context opened mid-run shows "Another window is driving this era — you are watching.", offers "Try to take over", has its speed, Dismiss and Join controls disabled, sends **no** write to the era (the requests are attributed per context; its only non-GET request is the denied `settings` stamp) and the database grows at the driver's pace with one position row per tick. "Try to take over" against a live driver gets HTTP 200 with zero rows. Closing the driver's window frees the lease within a fraction of a second (the unload release; the 30 s TTL is not waited for) and the watcher's "Try to take over" now succeeds, continuing at the next tick. `sessions.driver_id` is checked at every step.
- **d) Reload persistence.** (1) An unread chat (the model reply is scripted once so the *app* writes it to the other villager's row): halted after one turn, reloaded; the UI shows tick 1, the next actor is the other villager (the cursor survived), their observation starts at "Tick 1." and contains what was said, and afterwards their inbox is empty (heard once). (2) A reload in the middle of a run: the UI shows the era's last tick, the next actor is the saved successor, the observation shows exactly the database's items, rows continue at the next tick, and the greeting is never read again.
- **e) End, "Continue from here", tamper.** Ending archives with ticks, stockpile, summary and title and a closing chronicle line. "Continue from here" creates "Era N, continued" with `parent_session_id` and `fork_tick` = the latest checkpoint tick, new villager rows equal to the checkpoint (position, needs, items, persona), the cursor remapped by name, the stockpile, one chronicle line and no copied history; the fork's first observation reads the checkpoint's tick and its first position rows continue from it. The archived parent is **untouched** (row counts and content hashes of every era-scoped table and its sessions row, before and after the fork ran). Memories follow the tick rule through PostgREST's parsing of the nested `or`/`and` filter: a parent memory written at the fork tick is in the villager's prompt, one written one tick later (and the real ones after the checkpoint) is not. After the checkpoint's fingerprint is tampered with in the database, the button asks for confirmation, then shows the plain-language fingerprint refusal and **nothing anywhere changes** (row counts and hashes of every table; the live era is not ended).
- **f) The `anon` key.** Every table the app reads answers 200; the writes the app makes (insert/update/upsert with `on_conflict`/delete, the jsonb columns) work; `settings` is **not** readable or writable (401, `42501`), so the OpenRouter key is not exposed; a malformed or wrongly signed JWT is refused. The lease claim is sent by the **real supabase-js client** to PostgREST and behaves: a fresh lease (5 s) is refused with HTTP 200 and no rows, a stale one (31 s), a free one, one without heartbeat and one's own are claimed, a heartbeat exactly 30 s old is stale and 1 ms newer is fresh (the `lte` boundary, evaluated on `timestamptz`). The URL is printed, e.g. `PATCH /rest/v1/sessions?id=eq.<era>&or=(driver_id.is.null,driver_id.eq.<me>,driver_heartbeat_at.is.null,driver_heartbeat_at.lte.<iso>)&select=*`, and the browser bundle's takeover request has the identical shape.
- **g) A failed bond write survives a reload (R7.1).** Runs on the fork era (the last live era), with both villagers stood where the world starts them (diagonally adjacent, nothing unheard: a SQL update, then a reload so the app reads it). (1) A healthy scripted chat: the two upserts are answered 2xx, the database holds the pair at the strength the app wrote (S1; both upserts name this era's two villagers, although the bond started from an earlier era's row), `localStorage['empire:dirty-bonds:v1']` is empty again. (2) `gateway.mjs` fault injection (`failNext`, off by default) answers the next `POST|PATCH /rest/v1/relationships` with 503 from the gateway, so PostgREST never sees them; the other villager answers with a scripted chat: both writes got 503 with strength S1+1 for the same pair, the database still holds S1 (stale), and `localStorage` holds exactly one row (that pair, S1+1, the era; ids, strength and timestamps only). (3) The fault is switched off and the page reloaded; nobody presses Begin: the app GETs the pair's strength, then sends one upsert with S1+1 answered 2xx, the database row becomes S1+1, the `localStorage` entry is removed, the lease stays free, and (after Begin) the next villager's prompt reads "bond S1+1", where the stale database said S1. (4) A second browser context whose `localStorage` was seeded with a dirty row (a fabricated strength of 10000, impossibly high on purpose so it is strictly above the database's) opens while the lease is held by a fake driver (a SQL update): it shows the watch banner and sends no write of any kind, no `relationships` write and no recovery read (the compare GET for the pair); its only `relationships` requests are the load-time bond GETs that `getRelationships` makes in every window to show the bonds (reads are allowed for a watcher; R7.6 forbids writes), the database is unchanged and the row stays in its `localStorage`; after the fake driver is cleared and "Try to take over" is pressed, its upsert carries exactly 10000, the database row follows and its `localStorage` entry is removed. **Does not prove:** a real network failure or an offline browser (the 503 is injected by our gateway, which is a transient error to the app exactly as a gateway 5xx would be), the permanent-error drop against a real foreign-key violation (unit-tested with the classifier only), the stale-row rule against a database another window has moved on (unit-tested; here the row is higher or equal), cross-tab behaviour (each context has its own storage), a reload that happens *while* a request is in flight (unit-tested: the row is stored before the request), and the real pagehide path (the page is reloaded by Playwright after the failure, not killed mid-request).

**Found and fixed by this run** (each with a unit test where the logic is extractable; see `git diff`):
1. **The roster order was ambiguous.** The starting villagers were seeded with one multi-row INSERT, so both rows got the same `created_at`; the roster is read `ORDER BY created_at` and the turn cursor means "the villager after X in join order". With a tie PostgreSQL may return either order, and a different one after an UPDATE moves a row (found by the e2e's own assertion that join order is strict). Now the cast is inserted one villager per statement (a failure removes the half-seeded cast) and both roster reads add `id` as a tie-break (so eras seeded by older builds are stable too). Test: a source guard in `persisted.test.ts`.
2. **A reload or closed tab sometimes left the era locked for up to 30 s.** The unload handlers released the lease through the supabase-js query builder, which looks up the auth session asynchronously before sending; a page that is unloading may stop running first, and the next window then showed "Another window is driving this era" until the TTL (about 1 reload in 10 here; 0 in 40 after the fix). The release is now a synchronous `fetch(..., { keepalive: true })` built by the pure `leaseReleaseRequest` (`driver.ts`). Tests: request shape, id safety, and a source guard that the unload handlers use it without awaiting.
3. **The right-hand panel's six tabs overflowed their 380 px panel** (Discoveries and Replay were drawn outside it and the page scrolled sideways when Replay was clicked). The tab bar now wraps (`flex-wrap`).

**Findings recorded:**
- `settings` is not readable by `anon` after the lock migration (intended: the key must stay private). The old deploy-version reset that read and stamped it on every load could never work, so it was removed; the e2e run now asserts the app makes no request to `settings` on load.
- Without Realtime, **the Chronicle and Records panels do not update while the era runs** (they are filled once per load and by realtime INSERTs only; there is no polling), nor do speech bubbles and event sounds for `say`. The island, the tick, the stockpile and the villager cards are driven by the in-memory simulation and keep working, and a reload fills the panels from the database. A **watching window's map and tick are frozen at what it loaded** (it has no realtime subscription for agents or world state; even with Realtime only the two feeds are subscribed); "Try to take over" reloads it.
- Every table except `settings` has `USING (true)` policies for `anon`: anyone holding the public anon key can read, rewrite or delete every era. This is the documented single-tenant design, not a defect of the migrations.

What it does **not** prove: Supabase Realtime delivery (refused here, so the live feed, `say` bubbles and sounds have no end-to-end test), a real language model (the brain is scripted; model quality and the live-model checks B1/C1/C2 stay in `npm run harness`), a real Supabase project (its auth service, Kong gateway and edge-function runtime are replaced by the gateway above; the Deno functions `agent-brain` and `settings-key` are not run; the scratch database has no `auth`/`storage` schemas and, unlike Supabase, **no default privileges** for the API roles, which is the stricter test of the migrations' own `GRANT`s), several real machines (all windows share one host, one clock and one database connection pool, so clock skew between drivers is not exercised: the TTL is evaluated from the clients' clocks for the claim and the database's for stored timestamps) and the TTL path in real time (a crashed driver's lease expiring after 30 s is covered by the boundary checks in f, not by waiting it out). The lease race itself (two simultaneous claims, exactly one winner) remains the job of `check:migrations`. The checks ran in Chromium with software WebGL; other browsers are not covered.
